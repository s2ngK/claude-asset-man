# 대출·예금·적금 계좌

← [그룹 가계부](README.md) · 관련 [데이터 모델](data-model.md) [인증과 그룹 격리](auth-and-scoping.md) [거래 등록 흐름](flow-create-transaction.md)

가계부는 **흐름(수입·지출)만** 다룬다. 남은 빚과 모아둔 돈은 어디에도 없었다.
`/accounts` 는 그 **잔액과 만기**를 보는 곳이고, **두 번째 가계부가 아니다** — 이 화면에서
거래를 만들지 않는다 (#44).

# 세 가지만 기억하면 된다

## 1. 잔액 컬럼이 없다

`accounts` 에 `balance` 가 없다. 잔액은 그 계좌에 연결된 거래에서 **매번 계산한다.**

손으로 갱신하는 숫자는 두세 달 뒤에 안 고치게 된다. 그러면 화면에 6개월 전 잔액이 남고,
**그건 없는 것보다 나쁘다.** 월 합계를 클라이언트 계산에서 서버로 옮긴 것과 같은 판단이다
([#14](https://github.com/s2ngK/claude-asset-man/issues/14) · [통계 집계 규칙](stats-rules.md)).

| 종류 | 잔액 |
|---|---|
| 대출 `loan` | `amount − Σ원금분` (0 아래로 안 내려간다) |
| 예금 `deposit` | `amount` — 목돈을 한 번 넣고 만기까지 그대로다 |
| 적금 `installment` | `Σ원금분` — 넣은 만큼이 잔액이다 |

**끝난 계좌(`matured`·`closed`)의 잔액은 0 이다.** 받았거나 다 갚았으니 남은 것이 없다.
그때의 확정 금액은 `settled_amount` 에 따로 남는다.

쿼리는 한 번이다 (`queries.account_totals`) — `group_id` 로 좁힌 뒤 `account_id` 로 묶는다.
계좌마다 따로 물으면 계좌 수만큼 나간다. 추이에서 한 번 겪은 N+1 이다
([#15](https://github.com/s2ngK/claude-asset-man/issues/15)).

## 2. 소유는 개인, 열람은 그룹

`accounts.user_id` 가 주인이다. 하지만 **목록은 그룹 전체가 함께 본다.**

거래와 **같은 규칙**이다 (→ [인증과 그룹 격리](auth-and-scoping.md)):

| | 누가 |
|---|---|
| 조회 | 같은 그룹이면 전부 |
| 만들기·고치기·지우기·정산 | **주인만.** 동료 것은 403, 다른 그룹 것은 404 |
| 거래를 그 계좌에 **연결**하기 | 같은 그룹이면 누구나 |

마지막 줄이 일부러 느슨하다. **배우자의 대출을 대신 갚는 것**은 공동 가계부에서 자연스럽다.
계좌의 조건(금리·만기·상환방식)을 바꾸는 것만 주인 몫이다.

## 3. `amount` 의 뜻은 `kind` 가 정한다

| kind | `amount` |
|---|---|
| `loan` | 대출 원금 |
| `deposit` | 예치 금액 |
| `installment` | **월 납입액** (잔액이 아니다) |

컬럼을 셋으로 나눌 수도 있지만 그러면 어느 행에서든 **둘은 항상 비어 있다** — "미래를 위한
빈 자리를 만들지 않는다" 는 원칙에 걸린다 (→ [그룹 가계부](README.md)).

대신 화면이 라벨로 뜻을 말한다 (`AccountModal` 의 `AMOUNT_LABEL`). 그리고 **종류는 만든 뒤
바꿀 수 없다** — 예금을 대출로 바꾸면 이 값의 뜻과 잔액 계산식이 통째로 달라져 이미 붙어
있는 거래들의 해석이 뒤집힌다.

# 상환 한 번은 거래 한 줄이다

`transactions` 에 두 칸이 붙는다.

| 컬럼 | |
|---|---|
| `account_id` | 이 거래가 움직이는 계좌. **대부분의 거래는 NULL 이다** |
| `interest_amount` | `amount` 중 이자분. 나머지가 원금분 |

50만원을 갚았고 그중 이자가 10만원이면 `amount=500000, interest_amount=100000` **한 줄**이다.
통장에 찍히는 모양과 같다.

> [!NOTE] 원금/이자를 두 줄로 쪼개지 않는 이유
> 목록에서 한 번 갚은 것이 두 줄로 보인다. 그리고 어느 줄이 원금인지를 **카테고리 이름으로**
> 판단하게 되는데, 이 저장소는 카테고리를 이름으로 매칭하다 이미 한 번 데였다
> ([#17](https://github.com/s2ngK/claude-asset-man/issues/17) · [거래 등록 흐름](flow-create-transaction.md)).

검증은 **저장 뒤의 상태**를 기준으로 한다 (`_check_account_fields`).

- 계좌 없이 이자분만 있으면 **422** — 그 값은 아무 데도 안 쓰인다
- 이자가 금액보다 크면 **422** — 원금분이 음수가 되어 잔액이 거꾸로 늘어난다
- 금액만 줄여도 앞뒤가 안 맞을 수 있으므로, 수정에서도 바뀐 값으로 다시 본다

# 계산은 예상치고, 확정은 사람이 한다

`src/lib/accounts.ts` 가 만기 수령액과 회차 상환액을 계산한다. **이 값은 어디에도 저장되지
않는다.** 화면의 기본값으로만 쓴다.

실제 금액은 **우대금리·중도해지이율·세금우대** 때문에 공식과 늘 어긋난다. 그래서 칸을
열어두고 사람이 고친다.

> [!IMPORTANT] 이 결정 하나로 스키마에서 이자 관련 필드가 거의 다 빠졌다
> 단리/복리 구분, 이자소득세율, 우대금리 조건 — 전부 **계산기의 입력일 뿐 저장할 것이
> 아니다.** 저장하는 것은 확정된 결과(`settled_amount`)뿐이다.

## 만기 예상액 (예적금)

- **예금** — 목돈을 한 번 넣으므로 `원금 × 월이율 × 개월`
- **적금** — 회차마다 예치 기간이 다르다. 첫 회차는 n개월, 마지막은 1개월 예치되므로
  이자는 `월납입액 × 월이율 × n(n+1)/2`

세후로 보여준다 (이자소득세 15.4%). 복리·우대금리는 넣지 않았다 — **여기서 정교하게 맞출수록
"계산이 맞는다" 는 잘못된 믿음만 준다.**

## 회차 상환액 (대출)

이자는 언제나 `남은 원금 × 월이율` 이다. 상환방식이 가르는 것은 원금을 얼마나 갚느냐다.

| 방식 | 원금 |
|---|---|
| `equal_payment` 원리금균등 | `월상환액 − 이자` |
| `equal_principal` 원금균등 | `원금 ÷ 전체 개월` |
| `bullet` 만기일시 | 0 (만기가 지나면 잔액 전부) |

> [!WARNING] 원리금균등의 월 상환액은 **대출 시점에 정해진 상수**다
> 원금과 **전체 기간**으로 낸다. 남은 잔액과 남은 개월로 다시 계산하면, 실제로 낸 금액이
> 스케줄과 조금만 달라져도 예상액이 매달 튄다 — 덜 갚으면 남은 기간에 몰려 상환액이
> 폭증한다. 1억 2천 24개월 3.6% 짜리가 8회차에 `7,093,679원` 으로 나온 적이 있다
> (맞는 값은 `5,189,653원`).

# 정산 — `POST /api/accounts/{id}/settle`

만기·중도해지를 확정한다. **금액은 사람이 넣은 값을 그대로 믿는다.**

- **예적금** — 확정 수령액에서 넣은 원금을 뺀 만큼을 **이자 수입 거래로 남긴다.** 그래야
  통계의 수입에 실제로 받은 이자가 잡힌다. 이자는 **계좌 주인의 수입**이다 (정산을 누가
  눌렀는지와 무관하다). 원금보다 적거나 같으면 0원짜리 줄을 만들지 않는다
- **대출** — 거래를 만들지 않는다. 상환은 회차마다 이미 입력돼 있고 조기상환도 거래 입력이다.
  여기서는 **끝났다는 사실만** 기록한다

이자 카테고리는 지정할 수 있고, 없으면 서버가 `금융수입` → `기타`(수입) 순으로 고른다.
지출 카테고리를 주면 404 다 — 이자는 수입이고, 지출로 잡으면 통계가 뒤집힌다.

카테고리를 **이름으로 매칭**하는 것과는 다르다. 저장되는 것은 언제나 id 이고, 여기서 이름은
기본값을 고르는 힌트일 뿐이다 (`move_transactions_to_fallback` 가 `기타` 를 찾는 것과 같은
성격 → [거래 등록 흐름](flow-create-transaction.md)).

# 지워도 거래는 남는다

`DELETE /api/accounts/{id}` 는 붙어 있던 거래의 **연결만 끊는다** (`account_id`,
`interest_amount` 를 NULL 로).

실제로 돈이 오간 기록이라 계좌를 정리한다고 가계부에서 사라지면 안 된다. 카테고리를 지울 때
거래를 `기타` 로 옮기는 것과 같은 방침이다
([#41](https://github.com/s2ngK/claude-asset-man/issues/41)).

끝난 계좌를 **기록으로 남기려면** 지우지 말고 정산한다. 상태 뱃지와 확정 금액이 목록 아래
"끝난 계좌" 에 접혀 남는다.

# 화면

`/accounts` — `AppNav` 항목이 3개에서 **4개**가 됐다 (→ [반응형 레이아웃](responsive-layout.md)).

- 상단 — **총 자산**(예적금 잔액 합) · **총 부채**(대출 잔액 합)
- 아래 두 구역 — 대출 / 예금·적금. 넓은 화면에서는 두 칸으로 나란히 선다
- 계좌 한 줄 = 이름 · 종류 · 주인 · 금리 · 잔액 · 진행 막대 · 만기까지 남은 개월
- 내 계좌는 왼쪽 초록 막대로 구분한다 — 목록의 내 내역과 같은 표시다

## 지출 통계는 건드리지 않았다

상환액이 지금처럼 **전액 지출로** 잡힌다. 원금 상환은 엄밀히는 소비가 아니라 자산 이동이지만,
이 앱은 현금흐름 가계부고 **통장에서 나간 것은 나간 것**이다.

"원금 상환 제외" 토글이 필요해지면 그때 단다. 지금 넣으면 사용자가 머릿속에 모델을 두 개
들고 있어야 한다.

## 목록 행의 계좌 뱃지는 왼쪽에만 붙는다

`TransactionItem` 이 연결된 계좌 이름을 보여주지만 **왼쪽 칸에만** 둔다. 오른쪽(금액) 칸을
건드리면 줄마다 끝이 어긋난다 — 호버 삭제 버튼으로 한 번 겪은 일이다
(→ [함정과 교훈](pitfalls.md)).

# v1 에 넣지 않은 것

- **상환 스케줄 표**(회차별 원금·이자 분해) — 원금·금리·기간·상환방식만 있으면 그때그때
  계산되므로 **저장할 것이 없다.** 나중에 계산 함수만 얹으면 된다
- 중도상환수수료, 변동금리, 거치기간
- 단리/복리 구분, 이자소득세율 저장 — 위 "확정은 사람이 한다" 로 불필요해졌다
- 만기 알림
- 순자산 추이 그래프
